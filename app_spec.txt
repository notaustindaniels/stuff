<project_specification>
  <project_name>White-Label Multi-Tenant Headless CMS, LMS & Community Platform</project_name>

  <overview>
    Build a comprehensive, white-label-able Multi-Tenant SaaS platform designed for course creators and educators. 
    The architecture utilizes a Cloudflare-native approach with Turso for per-tenant database isolation, ensuring true data sovereignty, 
    security, and blast radius containment (an attack on Tenant A affects ONLY Tenant A). 
    
    The system features a modular monorepo structure including a Headless CMS, Learning Management System (LMS), 
    Community Platform (Skool-like), Video Processing Pipeline (OpusClip-like), and AI-powered content generation. 
    It supports hierarchical roles (God-mode, Super-admin, Admin, User) and custom domain mapping via Cloudflare for SaaS.
    
    Each module is designed to be independently extractable from the monorepo for isolated development, 
    then seamlessly rejoined when consolidated development resumes.
  </overview>

      <r2_storage_partitioning>
        - Tenant-prefixed paths: /tenants/{tenantId}/files/...
        - Signed URLs for secure access
        - Per-tenant storage quota enforcement
        - Zero egress fees (major cost advantage)
      </r2_storage_partitioning>
      
      <tenant_provisioning_workflow>
        1. User purchases plan (Stripe checkout via Clerk)
        2. Webhook triggers Cloudflare Worker
        3. Worker calls Turso API to create new database
        4. Worker runs Drizzle migrations on new database
        5. R2 prefix automatically created on first upload
        6. Vectorize index created if RAG enabled
        7. User redirected to onboarding wizard
      </tenant_provisioning_workflow>

      </description>
      
      <workflow>
        1. Super-admin requests disable (provides legal document reference)
        2. God-mode admin reviews and approves
        3. Both parties confirm via secure authentication
        4. Immutable audit log entry created
        5. All god-mode access tokens for tenant revoked
        6. tenant.god_mode_enabled set to FALSE
        7. Email confirmation sent to all parties
      </workflow>
      
      <consequences>
        - Platform owner permanently loses technical support access
        - Tenant assumes full responsibility for their data
        - Cannot be re-enabled without new legal agreement and code change
        - Audit log permanently records the decision
        - Tenant explicitly waives technical support privileges
      </consequences>

        3. Job queued in Cloudflare Queues

        6. LLM analyzes transcript for clip-worthy moments
        7. FFmpeg generates clips with captions
        8. Optional: Flux.1 generates b-roll images

        10. PartyKit notification when processing complete
        11. User reviews clips in Airtable-style interface

        - Starter: 100 AI requests/hour
        - Growth: 500 AI requests/hour  
        - Enterprise: 2,000 AI requests/hour
        
        Note: Users pay their AI provider directly based on usage.
        These limits prevent runaway loops or abuse, not monetization.
        
        Graceful handling when exceeded:
        - "Rate limit reached, please wait X minutes"
        - No upgrade prompt (since BYOK means they control costs)
        - Auto-restore after cooldown
      </rate_limiting>
    </ai_content_engine>

  <security_and_resilience>
    <blast_radius_isolation>
      The Turso per-tenant architecture ensures:
      - Attack on Tenant A affects ONLY Tenant A
      - Resource exhaustion is tenant-scoped
      - Database corruption is isolated
      - No cross-tenant data leakage possible at infrastructure level
      
      Per-tenant isolated resources:
      - Turso database
      - R2 storage prefix
      - Vectorize index
      - PartyKit room namespaces
    </blast_radius_isolation>
    
    <circuit_breaker_pattern>
      Automatic tenant isolation under stress:
      
      1. Track failures per tenant (error rate, latency)
      2. Trip circuit after threshold (e.g., 10 failures in 1 minute)
      3. Open state: Return error immediately, don't hit database
      4. Half-open state: Allow single request to test recovery
      5. Closed state: Normal operation resumed
      
      Circuit state stored in Cloudflare KV or Durable Objects.
    </circuit_breaker_pattern>
    
    <edge_rate_limiting>
      Implemented in Cloudflare Workers:
      
      Per-Tenant Limits:
      - Prevents one tenant's traffic spike affecting others
      - Separate counters per tenant
      - Configurable per subscription tier
      
      Per-User Limits:
      - Prevents one user affecting entire tenant
      - Separate counters per user within tenant
      - Stricter limits for unauthenticated requests
      
      Response Headers:
      - X-RateLimit-Remaining
      - X-RateLimit-Reset
      - Retry-After (on 429)
    </edge_rate_limiting>
    
    <graceful_degradation>
      When limits exceeded, preserve core functionality:
      
      AI Limit Exceeded:
      - Disabled: AI generation, suggestions, RAG queries
      - Preserved: Course access, community, basic CMS
      - Message: "AI features temporarily unavailable"
      - Auto-restore: After cooldown or billing reset
      
      Storage Limit Exceeded:
      - Disabled: File upload, video upload
      - Preserved: All read operations, course access
      - Message: "Storage limit reached. Delete files or upgrade."
      - No auto-restore (requires action)
      
      Video Processing Limit:
      - Jobs queued, not rejected
      - Clear queue position indicator
      - Option to purchase additional credits
    </graceful_degradation>
    
    <ddos_protection>
      Cloudflare provides edge protection:
      - Volumetric attacks absorbed at edge (280+ Tbps capacity)
      - WAF rules for application-layer attacks
      - Bot detection and challenge
      - Per-hostname rate limiting
      
      Platform provides origin protection:
      - Turso not directly exposed (requests via Workers only)
      - Tenant-aware rate limiting at application level
      - Circuit breakers prevent cascade failures
      - Anomaly detection for unusual patterns
    </ddos_protection>
  </security_and_resilience>

  <key_interactions>
    <tenant_provisioning_flow>
      1. Visitor lands on marketing site
      2. Selects pricing tier, clicks "Get Started"
      3. Redirected to Clerk sign-up (embedded or hosted)
      4. After sign-up, Stripe Checkout for payment
      5. Stripe webhook received by Cloudflare Worker
      6. Worker validates webhook signature
      7. Worker calls Turso API: createDatabase({name: tenant-{id}, group: production})
      8. Worker waits for database ready
      9. Worker runs Drizzle migrations on new database
      10. Worker creates tenant record in platform database
      11. Worker creates Clerk organization, adds user as owner
      12. User redirected to onboarding wizard in dashboard
      13. Onboarding: Set community name, upload logo, invite first admin
    </tenant_provisioning_flow>
    
    <course_creation_flow>
      1. Admin clicks "Create Course" in dashboard
      2. Enters title, description, selects pricing model
      3. Course created in draft status
      4. Admin adds modules via sidebar
      5. Within modules, adds sections
      6. Within sections, adds lessons
      7. For video lesson: Uploads to R2, system generates thumbnail
      8. For quiz: Uses quiz builder UI
      9. Sets drip schedule if applicable
      10. Previews as student
      11. Clicks "Publish" - course goes live
      12. Students can now enroll
    </course_creation_flow>
    
    <student_enrollment_flow>
      1. Student visits course landing page (public or within community)
      2. Clicks "Enroll" button
      3. If free: Immediate enrollment
      4. If paid: Redirected to Clerk-embedded Stripe checkout
      5. After payment: Webhook creates enrollment record
      6. Student redirected to course player
      7. First lesson auto-starts
      8. Progress tracked as student advances
      9. Drip content unlocks based on schedule
      10. On completion: Certificate auto-generated
      11. Student can share certificate to LinkedIn
    </student_enrollment_flow>
    
    <video_clipping_flow>
      1. User navigates to Video Processor
      2. Pastes YouTube URL in input field
      3. System validates URL format
      4. System checks user's video processing credits
      5. If insufficient: Prompt to purchase credits
      6. User confirms processing
      7. Job created with status "queued"
      8. Cloudflare Queue receives job message
      9. Worker picks up job:
         a. Updates status to "downloading"
         b. YT-DLP downloads video via Evomi proxy
         c. Uploads raw video to R2
         d. Updates status to "transcribing"
         e. Whisper generates timestamped transcript
         f. Updates status to "analyzing"
         g. LLM identifies clip-worthy segments
         h. Updates status to "clipping"
         i. FFmpeg generates clips
         j. Optional: Flux.1 generates b-roll images
         k. Optional: Image-to-video converts b-roll
         l. Updates status to "completed"
      10. PartyKit sends real-time notification to user
      11. User reviews clips in Airtable-style interface
      12. User can trim, add captions, select b-roll
      13. User exports clips in platform-specific formats
      14. After 30 days: Cron job deletes processed files
    </video_clipping_flow>
    
    <rag_agent_query_flow>
      1. Community member types "@Agent what is...?" in chat
      2. PartyKit server intercepts message with @Agent mention
      3. Validates user has RAG access (unified course access required)
      4. Checks user's daily query limit
      5. Extracts query text after mention
      6. Calls Workers AI to embed query text
      7. Queries tenant's Cloudflare Vectorize index
      8. Retrieves top 5 most similar content chunks
      9. Constructs prompt:
         - System prompt from tenant's RAG config
         - Retrieved context
         - User's query
      10. Calls LLM via OpenRouter (or BYOK)
      11. Parses response, extracts citations
      12. Posts response to chat thread
      13. Includes source links if cite_sources enabled
      14. Logs query to ai_usage table
    </rag_agent_query_flow>
    
    <funnel_ab_test_flow>
      1. Admin creates landing page in builder
      2. Clicks "Create A/B Test" on page
      3. Defines goal metric (click, submission, purchase)
      4. Sets goal selector (CSS selector for click/form)
      5. Creates Variant B (duplicates current page)
      6. Edits Variant B in builder
      7. Sets traffic split (e.g., 50/50)
      8. Clicks "Start Test"
      9. Visitors randomly assigned to variants
      10. Assignment stored in cookie for consistency
      11. Conversions tracked against each variant
      12. Dashboard shows running stats
      13. When statistical significance reached: Alert
      14. Admin reviews results
      15. Admin declares winner or continues test
      16. Winner variant becomes default page
    </funnel_ab_test_flow>
  </key_interactions>
